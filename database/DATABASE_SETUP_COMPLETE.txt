DATABASE TABLES CREATED (6)
═══════════════════════════════════════════════════════════════════════════════

1. PRODUCTS
   └─ Product catalog for customer enquiries
   ├─ Fields: id, name, price, description, image_path, is_active, timestamps
   ├─ Access: Public read (active only), Admin CRUD
   └─ Constraints: price >= 0, NOT NULL fields

2. PRODUCT_ENQUIRIES
   └─ Customer interest tracking for follow-up
   ├─ Fields: id, product_id (FK), customer_*, enquiry_status, created_at
   ├─ Access: Public insert, Admin read/update
   └─ Constraints: Valid status enum, product must exist

3. SERVICES
   └─ FIXIT services offered (screen repair, battery, etc.)
   ├─ Fields: id, service_name, description, icon_path, is_active, display_order, timestamps
   ├─ Access: Public read (active only), Admin CRUD
   └─ Constraints: service_name NOT NULL

4. STORE_INFORMATION
   └─ Business contact and operational details
   ├─ Fields: id, business_name, phone, whatsapp, email, address, hours, map coords, about, timestamps
   ├─ Access: Public read, Admin CRUD
   └─ Constraints: business_name NOT NULL (typically 1 row)

5. SECOND_HAND_LISTINGS
   └─ PRIVATE user-submitted listings for old products (NOT marketplace)
   ├─ Fields: id, seller_*, product_name, condition, description, price, status, email_verified, token, timestamps
   ├─ Access: Admin only (completely private)
   ├─ Constraints: Valid condition/status enums, price >= 0, email required
   └─ Workflow: NEW → REVIEWING → CONTACTED → ACCEPTED/REJECTED → COMPLETED

6. SECOND_HAND_IMAGES
   └─ Images for second-hand listings (up to 4 per listing)
   ├─ Fields: id, listing_id (FK), storage_path, image_order (1-4), is_thumbnail, created_at
   ├─ Access: Admin only (completely private)
   ├─ Constraints: max 4 images, only 1 thumbnail, unique (listing_id, image_order)
   └─ Triggers: enforce image limit, enforce single thumbnail

Follow SUPABASE_SETUP.md for detailed instructions:

STEP 1: Create Supabase Project
  → Go to supabase.com, create new project
  → Save: Project URL, Anon Key, Service Role Key

STEP 2: Run SQL Migrations
  → Open Supabase SQL Editor
  → Run migrations/001_initial_schema.sql
  → Run migrations/002_rls_policies.sql
  → Run functions/backend_operations.sql

STEP 3: Create Storage Buckets
  → Create 3 buckets: products, second-hand, service-icons
  → Set correct visibility: public/private

STEP 4: Configure Storage RLS
  → Add policies to each bucket
  → Restrict second-hand to admin only

STEP 5: Configure Authentication
  → Enable Email/Password auth (default)
  → Allow email signup

STEP 6: Create Admin User
  → Authentication > Users > Add User
  → Email: your-admin@example.com
  → Password: strong password

STEP 7: Set Admin Metadata
  → Select admin user
  → User Metadata tab
  → Add: {"is_admin": true, "role": "admin"}

STEP 8: Enable RLS
  → Database > Roles
  → Verify RLS enabled on all tables

STEP 9: Configure Email Verification
  → Authentication > Email Templates
  → Customize confirmation email

STEP 10: Verify Database Setup
  → SQL Editor > Run verification queries
  → Confirm all tables/policies present

STEP 11: Load Sample Data (Optional)
  → Run seed/sample_data.sql
  → Test with sample products/services

STEP 12: Document Configuration
  → Save Project URL, Anon Key
  → Save admin email/password securely
  → Share with backend developer

═══════════════════════════════════════════════════════════════════════════════
CRITICAL INFORMATION FOR BACKEND DEVELOPER
═══════════════════════════════════════════════════════════════════════════════

1. NEVER COMMIT SECRETS
   └─ Supabase keys must NOT be in .env files in git
   └─ Use environment variables or secret management system

2. IMAGE COMPRESSION IS REQUIRED
   └─ Database does not accept raw image data
   └─ Backend must compress before upload
   └─ Only storage_path references stored in DB

3. EMAIL VERIFICATION IS MANDATORY
   └─ Second-hand sellers MUST verify email
   └─ No listing can be accepted without verification
   └─ Backend generates token, sends email, calls verify function

4. RLS POLICIES ENFORCE SECURITY
   └─ Cannot query second-hand listings as public user
   └─ Cannot see other customers' enquiries
   └─ Cannot access private storage buckets
   └─ Admin must be properly authenticated

5. LISTING WORKFLOW IS CRITICAL
   └─ Status: NEW → REVIEWING → CONTACTED → ACCEPTED/REJECTED → COMPLETED
   └─ Each status has specific meaning
   └─ Admin controls status progression
   └─ Never automatically accept listings

6. FOREIGN KEYS ARE ENFORCED
   └─ Cannot create enquiry for non-existent product
   └─ Cannot create image for non-existent listing
   └─ Deleting parent cascades to children (e.g., listing → images)

7. CONSTRAINTS ARE ENFORCED
   └─ Cannot set negative prices
   └─ Cannot set invalid status values
   └─ Cannot add > 4 images per listing
   └─ Database rejects violating records
